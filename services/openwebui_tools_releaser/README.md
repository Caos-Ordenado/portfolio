# Open WebUI tools in-cluster releaser

One-shot outbound-only controller (stdlib Python 3.13; no pip dependencies). It checks the public GitHub `main` ref, then the **newest** `push` run on `main` for the trusted `openwebui-tools trusted deploy` workflow (not just completed runs). The run must be for current HEAD, completed successfully, with a successful `build` job. A pending, failed, gate-skipped, or older run never falls back to a prior success. It checks the public commit status and anonymous GHCR manifest for the matching digest and rechecks main HEAD before patching **only** the existing `default/openwebui-tools` Deployment's named container image, pull policy, and attempted-run annotation. It does not create or apply Kubernetes objects or serve HTTP. The workflow's reviewed source-only gate is the trust boundary; do not broaden it without re-reviewing this controller.

## Prerequisites and rollout

- Review/pin the **controller image itself** manually before running: it is a high-trust dependency with Deployment patch permission. Build/import natively on `caos`, verify its OCI manifest digest in MicroK8s containerd, and pin that digest in the CronJob (see `k8s/openwebui_tools/RELEASER.md`). Do not automatically self-update the controller from the app's image stream.
- GHCR package `ghcr.io/caos-ordenado/openwebui-tools` must be public for anonymous token/manifest access and anonymous node pulls. Private/unauthorized registry responses fail closed.
- Keep the reviewed `main` push branch checks, source-only gate, pinned build inputs and `build` job name in `portfolio/.github/workflows/openwebui-tools-deploy.yml`. The workflow owner must publish a GitHub commit status **only after a successful anonymous GHCR push** using `GITHUB_TOKEN` with `statuses:write`: context exactly `openwebui-tools-image`, state `success`, description exactly the published `sha256:<64 lowercase hex>` digest, target URL exactly `https://github.com/Caos-Ordenado/portfolio/actions/runs/<run_id>`, creator login `github-actions[bot]`. Statuses are append-only: the controller considers the newest matching context on the commit; missing, superseded, malformed, or differently authored statuses fail closed. A status is a high-trust GitHub workflow assertion, **not cryptographic image provenance**. GitHub Apps or other jobs able to append statuses as `github-actions[bot]` can impersonate it; restrict `statuses:write` and review branch/workflow changes. A compromised workflow, package, or GitHub/registry trust boundary can still cause a malicious rollout.
- Provision a dedicated ServiceAccount in `default` with a projected token and CA mounted at `/var/run/secrets/kubernetes.io/serviceaccount/`. Bind only `get,patch` on the **named** `deployments.apps/openwebui-tools` and `get` on the **named** `services/openwebui-tools` (no list/watch, Secrets, or pod privileges). Use normal Kubernetes in-cluster `KUBERNETES_SERVICE_HOST` and `KUBERNETES_SERVICE_PORT`. This directory intentionally does not apply or ship cluster manifests; review existing RBAC before use.
- Home MicroK8s now runs `RBAC,Node`; this ServiceAccount's named GET/PATCH and Service GET are permitted, while Secrets, other Deployments, pod exec and lists were denied. One-shot rollout and manual rollback both passed before the owner-approved recurring activation; recheck effective permissions after any RBAC change. Its current CA lacks a key-usage extension required by Python 3.13 strict X.509 mode: only the in-cluster Kubernetes TLS context clears `VERIFY_X509_STRICT`, while still requiring the mounted CA and verifying the hostname. External GitHub/GHCR requests retain default strict TLS. See `k8s/openwebui_tools/RELEASER.md`.
- Configure an operator-managed CronJob with `concurrencyPolicy: Forbid`, bounded job duration (allow at least 11 minutes for failed rollout plus restore), nonroot/read-only filesystem, no extra mounted secrets, and image digest pinning. Do not configure a Service/Ingress. Disable the old GitHub-hosted kubeconfig deploy step before enabling the CronJob so two controllers do not contend. No GitHub token, app key, or kubeconfig is needed in the controller.
- Verify locally: `python3 -m unittest discover -s tests -v` (from this directory); optionally `docker build --platform linux/amd64 -t openwebui-tools-releaser:local .`. No cluster changes are made by either command.

## Operations and recovery

Check CronJob Job completion and logs for `event=rollout_ready`, `event=run_already_attempted`, or `event=no_eligible_build`; failure exits nonzero with fixed reason codes, never token/response bodies. Inspect `kubectl -n default get deployment openwebui-tools` and `kubectl -n default get service openwebui-tools` (`ClusterIP` required). The initial JSON Patch atomically tests resourceVersion, container name/image/pull policy (and previous marker, if any) before setting the metadata annotation `automation.reyops.com/openwebui-tools-attempted-run-id` alongside the image/pull policy. Any run ID less than or equal to the marker is skipped even after manual image rollback. An eligible rollout polls Deployment GET until observed generation and updated/ready/available replicas match desired. The controller does not watch/list; a successful Job proves only that the Deployment was ready at the time of inspection, not ongoing health.

On an error after an attempted patch (including lost response), it GETs the live Deployment and restores the previous image/pull policy only if the named container **and attempt marker** still match its proposed values; the conditional restore tests the live resourceVersion and retains the attempted-run marker. Rollback is itself polled for readiness. Any restore failure logs `event=restore_failed_manual_inspection_required`: suspend the CronJob, inspect Deployment and pods, and manually restore the previously known good digest/policy if safe. For a planned rollback, suspend the CronJob first, patch the Deployment back to a reviewed digest, and confirm readiness before resuming. Reset/remove the attempt marker **only after operator review** of the run, digest, and reason to deliberately retry; a same-image/marker concurrent writer still cannot be distinguished on an uncertain patch response. Avoid other Deployment writers and review concurrent rollout events before recovery.

GitHub API rate limits, incomplete job windows (>100 jobs), missing status beyond the newest 100 statuses, invalid response shapes, and unavailable GHCR fail closed. Only the newest workflow run is considered. Kubernetes and external requests use 10-second per-request timeouts; rollout and restore each have a 300-second readiness deadline. Job-level active deadline should exceed these plus the bounded GitHub/registry calls.
